# 工程题 AI harness 集成实验

本分支是本地实验，基于 `ljy_feat/agent-learning-experiment` 并纳入多文件工程题支持。目标是让助教在考生明确授权后，能在公开工程工作区里运行命令或修改文件，同时留下可核查的操作记录。

## 选型与边界

实验采用 [mini-SWE-agent](https://github.com/SWE-agent/mini-swe-agent) 2.4.6 的 `DefaultAgent`、`LitellmModel` 和 `DockerEnvironment`。它提供现成的模型、命令执行和循环控制；项目只实现考试权限、文件同步、持久化和 UI。没有将其整套部署到 Django Web 进程，而是交给专用 Celery worker。原有问答与审查流程继续处理“只回答”请求。

每轮考生显式选择“只回答 / 运行 / 修改”。`closed` 禁止 AI；`limited` 只能回答，服务器拒绝运行与修改；`open` 中的工程题才可将运行或修改送入 harness。文件级修改还要求指定当前文件。工程运行结束后不写回任何文件；工程修改仅在 agent 正常提交结果、文件仍是原版本、且改动没有越过授权范围时写回 `WorkspaceFile`，并生成 `CodeChange`。工作区只装载题目公开文件，不装载隐藏测试和评分材料。

执行容器使用无网络、只读根文件系统、非 root 用户、去除 Linux capabilities、进程/CPU/内存限制以及临时工作区。模型请求在 worker 中发起，API 密钥不进入执行容器。worker 持有 Docker socket，因此它本身必须是受信任的服务；这一点需要在正式部署环境单独审查。

## 请求与记录

1. `POST /api/v1/agent/sessions/{id}/messages` 提交 `content`、`action`，修改时附 `scope` 与 `activeFile`。工程运行/修改返回 HTTP 202 和 `jobId`。
2. 前端轮询 `GET /api/v1/agent/sessions/{id}/jobs/{jobId}`，显示状态、步数与最终回复；`POST .../cancel` 可停止任务。已在执行中的模型调用要到下一次命令边界才会响应停止。
3. 服务器保存 `AgentHarnessJob`、各条命令的 `AgentToolCall`、最终 `AgentMessage` 和实际写回的 `CodeChange`。报告把考生请求、AI 实际修改和运行请求分开；构建失败不会被记为成功构建。报告不据此推断学生是否掌握知识。

部署时设置 `AGENT_PROJECT_HARNESS_ENABLED=1`，并配置 `DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、`AGENT_HARNESS_MODEL`。先构建工程题运行镜像，再用 Compose 启动 `agent-worker`。默认最多三条 worker 任务并行，每个执行容器限制 768 MiB、1 CPU；这只约束执行容器，不代表模型 API、MySQL、Redis 与 Web 进程的总资源上限。

## 本地实测

用 Arch Lab 的公开 handout 导入工程题，模拟一名考生通过项目 API 发出两轮请求，模型为网关上的 `DeepSeek-V4.1-Flash-1017`：

| 本轮请求 | agent 自行结束后的可核查结果 |
| --- | --- |
| 仅在 `sim/misc` 运行 `make yas`，不改文件 | 执行 3 步，报告编译到链接阶段时出现 `lineno` 重复定义，`make` 退出码为 2；数据库工作区无改动。 |
| 只将 `PartA/sum.ys` 首行注释改为指定文本，不运行测试 | 执行 3 步，只写回 `PartA/sum.ys`；没有运行测试。 |

两轮报告将调试提问记为 1 次、局部编程请求记为 1 次，并指出“无法判断学生是否独立完成了后续工作”。本地报告生成成功。另一次独立的 Arch Lab 可行性长实验中，mini-SWE-agent 自行结束并经独立自动评分取得 87.67/100；那是完整作业能力测试，不能等同于本平台在每轮授权限制下的成绩。长实验出现过 96 次调用后的网关连接错误，也产生了很大的模型上下文；正式使用需监控费用、延迟和中断恢复。

本分支的回归验证：后端 `agent problem judge` 原有及新增测试共 129 项，其中 7 项按既有条件跳过；前端生产构建通过，Compose 配置解析通过。上述实验为真实模型与隔离容器的 API 级测试，尚未代表整套生产 Compose 部署的负载测试。

## 六个作业文件的逐轮平台实验

同一模拟考生通过平台接口依次请求 Part A 的三个程序、Part B 的 `iaddq`、Part C 的 PIPE `iaddq` 与 `ncopy`。每轮只授权修改一个文件，运行和编辑的每条命令都保留在服务端。最后另有两次针对 `ncopy` 的追问：先确保正确，再根据 CPE 测量结果要求提速。这些请求是本地实验脚本模拟的考生提问，不是生产课程成绩。

| 阶段 | 观察结果 |
| --- | --- |
| Part A 三文件 | 分别自行提交；每轮只写回目标文件。 |
| Part B `seq-full.hcl` | 初次运行 `make clean` 删除了随题公开的可再生 C 文件，原同步器拒绝写回；修正后重试并自行提交。 |
| Part C `pipe-full.hcl` | 早期一次遇到命令日志编号冲突，一次触及 45 步上限；修正编号并给足时间后，19 步自行提交，只写回目标文件。 |
| Part C `ncopy.ys` | 宽泛的优化请求在约 224 步、782 秒后仍未收敛，且沙箱中有授权外文件变化，服务端拒绝写回。拆成“先保证 68/68 正确”的追问后，36 步自行提交，只有目标文件写回。 |
| 再追问性能 | 从已正确的 2 倍展开版本尝试 4/8 倍展开，100 步后仍无正确且更快的候选；任务状态为 `partial`，没有覆盖先前的正确版本。 |

私有评分器只读取平台数据库中**实际保存**的六个文件。最终结果是 **60/100**：Part A 20/20、Part B 30/30、Part C 的回归与正确性 10/10、性能 0/40。两种 `ncopy` 正确性检查均为 68/68，长度 267 字节，平均 CPE 从题包基线的 15.18 降至 11.85；课程性能规则要求 CPE 不高于 10.5 才开始计分。独立 harness 曾得到 87.67/100、CPE 8.42，但平台逐轮实验没有复制这个高分。两种结果必须分开引用。

这个平台会话一共 13 次工程请求：8 次提交、4 次失败、1 次未完成，记录 556 步操作。已记录输入 token 至少约 621 万、输出 token 至少约 5.27 万；早期失败轮次尚未计入，故这是下界。失败轮次计量缺口已修复。较宽泛的 `ncopy` 优化耗时和 token 显著高于聚焦正确性的请求；观察到一次长上下文模型调用维持 HTTPS 连接约两分钟后才继续，并非本地容器停滞。

## 范围控制与过程报告

当前分支进一步把“只做本轮所问”写为解答模型与独立审查模型共用的通用规则，并给出询问现状、诊断报错、请求思路、明确要求实现、明确要求运行五类通用示例。学生提问无需附上“不要写代码、不要运行”等限制语。开放模式仅选“允许修改”时，普通题的写文件工具才会出现；写入前还会由独立 Qwen 对本轮问题与拟写入差异做审查。工程题每条拟执行命令和最终改动仍由独立审查拦截。“允许修改”不再默认授权构建和测试，需另选“运行验证”。

先前用最长递增子序列做的预设回复模拟只覆盖普通算法题，不能证明工程 harness 的实际行为。随后改用同一份 Arch Lab 多文件题包与真实 `DeepSeek-V4.1-Flash-1017` 解答模型、`Qwen3.8-Flash` 护甲模型，从新会话分别跑完两种模式。开放模式会话 15：先询问 `PartA/sum.ys` 的现状，再明确请求实现该文件，工程 Agent 8 步后只写回该文件且未运行测试；下一轮明确请求编译运行，Agent 15 步后报告 YIS 停机与 `%rax=0xcba`，运行轮次没有持久化改动。受限模式完整会话 20：先问文件现状与当前节点/后继节点关系，学生在编辑器写入 `PartA/sum.ys`，AI 再解读现有文件；明确发出的 AI 修改和运行请求均返回 HTTP 403，全程没有 AI 写入或运行。两种模式均用只上传修改文件的正式工程提交进入 Docker 评分，`A_sum` 公开评分项通过；由于其余作业文件保持初始状态，整题均为 `partial`、21/100，而非声称整题完成。

真实流程揭示了回归问题并促成修复：工程题原本上传所有公开文件，超过 200 KB 限制后无法提交，现改为只提交相对题包初始版本有变化的文件；护甲模型曾把学生明确授权的 `make` 构建误拦截，也曾放行概念问答中附带的具体指令集细节，现分别补充了动作边界与概念边界的通用规则。报告模型原先只见到整题 `partial`，一度误把总成绩归咎于当前文件；现向其提供可公开的分项结果并要求区分整体与局部。新规则已用真实 Qwen 对原候选命令、回答和报告复测；本地保留的逐轮对话、命令和评分 JSON 位于被 Git 忽略的 `backend/tmp/arch-boundary-*.json`。护甲仍依赖模型判断，概念回答偶有超出提问深度，不能把本次通过当成绝对保证。

目前学生工作台提供公开文件编辑器，没有独立的终端入口。开放协作模式中，学生明确选择“运行”可让工程助手在隔离容器执行构建或脚本；受限模式的同类 AI 运行请求被拒绝。学生可以编辑已有公开脚本并提交，正式评分会运行教师配置的评分命令，但不能在工作台自行执行任意命令。

- `limited` 模式在 HTTP 服务端拒绝运行和编辑；`open` 的“只回答”仍由问答审查保护。工程运行不写回文件，单文件编辑只允许目标文件持久化；若 agent 未自行提交、越过步数/时间上限或出现授权外修改，草稿不应用。
- 独立 Qwen 审查先逐条检查工程 agent 拟执行的命令；拒绝的命令不会进入 Docker，并将整改理由返回 agent，连续三次拒绝即结束本轮。命令执行后，另对**拟写回的 diff**与本轮考生请求做语义比较；审查失败或结果格式无效时拒绝写回。单行请求只允许相关的局部改动，整文件请求可允许相应的较大 diff。审查规则不含具体题目特征，语义判断准确率仍需系统测量。
- 两种模式的问答都按学生实际提问控制深度；开放模式允许明确索要的代码，但只问当前文件时不应借题面扩展或推断未运行的结果。独立审查之外，服务端会拦住一些明确的越界表述并要求重写。学生报告改为连贯叙述提问、追问、实际回答和写回结果；提问领域次数单独列出，逐轮深度比较保留在内部 `systemReview`。服务端任务状态、命令记录、文件修改和提交记录优先于模型自述；证据片段必须出自对应学生原话。

本地浏览器实测：学生端切换工程文件后，编辑器内容与 AI 上下文路径一致；“只回答”可读取当前文件，“运行验证”经异步 worker 执行 `make yas` 并回报链接失败，“允许修改”只改 `PartA/sum.ys` 首行注释并写回编辑器。上述两轮工程任务分别约 18 秒和 13 秒自行完成。对“只根据当前文件说明”的问答曾两次出现额外推断，因此增加了证据范围提示和本地拦截；第三次不再引用题面，但仍产生一句未经运行的预测，现也纳入拦截条件。一次 7 问真实会话的报告生成成功，叙述了 2 次构建检查、2 次注释修改及 3 次文件状态询问。

这些机制能阻止未经授权的**持久化文件改动**，但不能证明所有语义越界都被模型审查发现。复杂工程任务也可能耗尽时间和 token 后仍未解决。正式使用前应决定单轮预算与教师可配置的长任务权限；考虑给工程题显式标注“可编辑文件”与“只读构建材料”，并为长任务设计经过审查的中途检查点。现有 Docker socket 仍是受信任 worker 的部署边界，3–5 人并发需要在实际服务器上做资源与网关限流测试。
